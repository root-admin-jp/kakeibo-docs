# Kakeibo 要件定義 v0.2

作成: 2026-11-07 / 状態: 決定事項反映済み（A1-A3, B1-B4, C 確定）
技術前提: API=Kotlin (Spring Boot 3), DB=MySQL 8, UI=Nuxt 3, UI/API分離 + モノレポ, GitHub `root-admin-jp/kakeibo`, クレデンシャルはコミットしない, DDL・ADR・要件定義はコミット可

## 1. 目的と利用範囲

- マネーフォワード風の家計簿Webアプリを自前で開発する。
- 将来一般公開の可能性があるため、最初からマルチユーザーサービスとして設計する。
- 共有・招待機能は不要（B3）。各ユーザーは自分の家計データのみを管理する。
- 通貨は JPY のみ、UI言語は日本語のみ（B4）。

## 2. ユーザーとテナント

- ユーザーはメールアドレス宛のワンタイムコード（OTP）で登録・ログインする（決定 O、ADR-0014。旧 B2 のパスワード方式は置き換え）。コードを受け取れることがメールアドレスの本人確認になる。ログイン後にパスキー（WebAuthn）を登録でき、パスキーのみでのログインも可能にする。パスワードは保持しない。
- サインアップ時に、そのユーザー専用のテナント（households、オーナー1名）を自動作成する。メンバー招待・共有は実装しない（ADR-0007）。
- 全ての口座・取引・カテゴリ・予算はテナントに属し、APIは認証ユーザーのテナントのデータしか返さない（ユーザー間データ分離）。

## 3. 口座・取引

### 3.1 金融機関マスタ（B1 確定リスト）
初期登録する機関（種別）:
- イオン銀行（銀行）、みずほ銀行（銀行）、PayPay銀行（銀行）、静岡銀行（銀行）、浜松磐田信用金庫（信用金庫）
- SBI証券（証券）
- モバイルWAON（電子マネー）、モバイルSuica（電子マネー）

### 3.2 口座 (accounts)
- 種別: 現金 / 銀行 / クレジットカード / 電子マネー / 証券 / その他
- 1口座は1テナントに属する。残高は取引から算出する（残高の直接編集はしない）。
- 証券口座はMVPでは残高・入出金の記録までとし、保有銘柄・評価額の自動管理はMVP外とする。

### 3.3 取引 (transactions)
既存の MF CSV Importer の列仕様 `日付, 収支種別（収入/振替/それ以外は支出）, 金額, 大項目, 中項目, 内容` と同じ意味で持つ。

| 項目 | 内容 |
|---|---|
| 日付 | 取引日 |
| 収支種別 | 収入 / 支出 / 振替 |
| 金額 | 円（整数、JPY） |
| 大項目 / 中項目 | カテゴリ2階層、テナントごとにカスタマイズ可 |
| 内容 | メモ・摘要 |
| 口座 | 出金元 / 入金先。振替は両方を持つ |

- 振替は収支集計に含めない（二重計上防止）。
- 削除は論理削除とし、集計から除外する。

### 3.4 カテゴリ
- 大項目・中項目の2階層、並び順つき、初期値はマネーフォワード風の一般的なもの。
- CSVインポートで未知のカテゴリが出た場合は「未分類」とし、取り込み結果レポートで知らせる。

## 4. 機能（MVP、C確定）

1. 登録・ログイン（メール OTP ／ パスキー）
2. 口座管理（作成・編集・一覧）
3. 取引 CRUD（一覧、月別・口座別・カテゴリ別フィルタ）
4. カテゴリ管理
5. 月次ダッシュボード（収入・支出合計、カテゴリ別グラフ、前月比）
6. CSVインポート / エクスポート（第1対応は汎用/MF形式CSV）

MVP外: 予算アラート通知、レシートOCR、保有銘柄管理、金融機関との自動連携（本番接続）、共有・招待、Googleログイン、多通貨・多言語。

※ 予算機能は DDL には含めるが、MVP画面に含めるかは実装順序で調整する。

## 5. 金融機関連携（B1）

- 銀行ID・パスワードを預かるスクレイピング方式は採用しない。
- Phase 1: CSVインポート + 手入力 + モック連携アダプタ（本フェーズで合意済み）。
- Phase 2: 対象8機関について、公式にダウンロードできるCSV/明細形式を機関ごとに調査し、形式別インポートマッピングを追加する。モバイルSuica / モバイルWAON は公式取得手段が限定的な可能性があるため、調査結果次第では汎用CSV・手入力対象とする。
- Phase 3: `InstitutionConnector` インターフェース経由で、公式アグリゲーターや銀行公式APIへ差し替え可能にする（ADR-0006）。
- 金融機関の認証情報は DB に保存しない。

## 6. 非機能要件

- セキュリティ: クレデンシャルは `.env` / 環境変数のみ、リポジトリには `.env.example`（ダミー）のみ。将来公開時は HTTPS 前提とし、OTP・パスキーのレート制限や監査ログを別途 ADR で追加する。
- 実行環境（当面）: ローカル開発のみ。docker-compose で MySQL 8 + API + Web。
- API/UI契約: REST + OpenAPI 3。UIは OpenAPI から型を生成して使う。UIからDBへ直接アクセスしない。
- データ分離: 全クエリはテナント境界を必須とする。テナントをまたぐ参照はエラーとする。

## 7. 受け入れ基準（MVP）

- docker-compose で DB / API / Web が起動し、登録→ログイン→口座作成→取引登録→月次ダッシュボード→CSV入出力が一通り動く。
- 他ユーザーのデータがAPIレスポンスに含まれないことをテストで確認する。
